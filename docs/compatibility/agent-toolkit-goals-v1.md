# Agent Toolkit Goal v1 compatibility

Veasel accepts the portable Goal v1 JSON emitted by `agent-toolkit goal
export`. The canonical contract and validator live in
[`ulises-jeremias/agent-toolkit`](https://github.com/ulises-jeremias/agent-toolkit),
not in a second Veasel schema implementation.

## Verified upstream source

- Repository: `ulises-jeremias/agent-toolkit`
- Current upstream main inspected on 2026-11-27: `f0290c17090ec4ee474bd9871aa4a2350c321ae1`
- Canonical schema: `schemas/goal-v1.schema.json`
- Current upstream also defines `schemas/goal-v2.schema.json` and
  `schemas/goal-evidence-v1.schema.json` at that commit. Veasel currently
  documents Goal v2 admission separately in
  [`agent-toolkit-goals-v2.md`](agent-toolkit-goals-v2.md); its permission
  ceilings are outside this Goal v1 compatibility claim.
- Canonical export: `modules/agent_toolkit_core/goals.v` (`goal_manifest_json`)
- CLI dispatch: `modules/agent_toolkit_cli/dispatch.v` (`goal export`)
- Source fixture: `tests/fixtures/goals/minimal.yaml`
- Exported golden fixture in this repository: `testdata/agent-toolkit-goal-v1-export.json`
- Golden fixture SHA-256: `2af34051ae3338c0f6f5845b05e9085fbf32899d0038a243998a17776cc401af`

The golden file was generated by building the native CLI from Toolkit commit
`871164134f1a798a7d08ffb27b0ce7a97c74d131` and running:

```sh
agent-toolkit goal export tests/fixtures/goals/minimal.yaml
```

Its values are illustrative fixture data; in particular, the repository path
and base SHA do not claim a live checkout or execution. The fixture verifies
wire compatibility only and is never execution evidence.

## Compatibility behavior

Veasel decodes the exported object into its Goal v1 admission type, applies its
own security and repository preflight, persists the manifest, and projects the
same authorized repositories, acceptance criteria, budgets, delivery mode,
task order, dependencies, paths, runner/verifier identities, and base SHAs.
Admission does not imply that a task ran or that a change was verified.

Veasel also accepts the optional task fields `verifier_provider` and
`verifier_model` as a paired routing extension. Existing Toolkit v1 exports
without these fields remain admissible and round-trip with empty route values.
Dispatch of `independent-review` requires an explicit pair; Veasel will not
silently reuse the implementation route and call it independent. These fields
express the requested route. The runtime checks supported adapters before
launching a bound read-only reviewer and verifies that the persisted run used
the requested route. It rejects an `independent-review` run whose provider and
model both match the implementation operation. This enforces distinct
configured route strings only; provider aliases, proxies, and model aliases
may still resolve to the same underlying service or model family. Installed
CLI reviewers run in `ask` mode, so their requested native tool actions remain
subject to Veasel approval and may pause until the user responds.

Compatibility currently covers the canonical fields emitted by `goal export`.
Although the upstream JSON Schema permits additional properties, Veasel's
Goal v1 decoder does not preserve extension fields during admission and
re-encoding. Consumers must not rely on round-tripping extension properties
until Veasel adds explicit support for them.

Goal evidence receipts remain a separate interoperability gap. Toolkit's
current `goal-evidence-v1` requires `task_id`, `attempt`, `repository`,
`base_sha`, `candidate_sha`, `mode`, `environment`, `verifier_identity`,
`verifier_version`, `result`, and at least one `sha256:` digest. Veasel's
internal verification receipt and schema-45 operator-acceptance record do not
yet serialize or validate that portable object. Operator acceptance is not
verifier evidence. Add and review an explicit adapter that binds the portable
receipt to the persisted candidate and verifier run before claiming
`draft_ready`; fixture receipts must never count as real provider, worker, or
product acceptance.
