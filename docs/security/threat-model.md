# Veasel Code threat model

**Scope:** Local V backend, OpenTUI client, SQLite sessions, configured model
providers, and the proposed repository-tool boundary
**Date:** 2026-10-13
**Modeler:** Codex
**Architecture source:** `docs/IMPLEMENTATION_PLAN.md`, `api.v`, `provider.v`,
`store.v`, `workspace_edits.v`, `main.v`, `tui/src/solid/main.tsx`, `tui/src/api-client.ts`
**Version:** unreleased branch
**Previous model:** Initial

## Architecture overview

- **Assets:** provider credentials in the backend environment or local model
  settings file; user prompts and
  model replies in SQLite; workspace source files; tool arguments and output;
  event history; session directory metadata.
- **Trust boundaries:** user ↔ TUI; TUI ↔ loopback HTTP API; V backend ↔ SQLite;
  V backend ↔ configured external model provider; future agent ↔ repository
  content and future tools.
- **Data flows:** TUI sends prompts and explicit edit approvals over loopback HTTP; V validates the request,
  loads recent session history, sends it to the configured provider over HTTPS
  (or user-configured loopback HTTP), then transactionally stores the user and
  assistant turns and emits replayable event IDs. The session agent may call bounded workspace list, read, literal search, and
  file-edit proposal tools; requested file excerpts and tool results are sent
  to the configured provider. Proposed file contents remain in SQLite until a
  user reviews the diff and explicitly approves the session-scoped operation.
- **Actors:** local user, other processes under the same OS account, browser
  origins reaching loopback, configured model provider, and future repository
  content that may contain adversarial instructions.

## Attack paths

1. Same-user local process → loopback API without Origin → session data access.
2. User session → configured external provider → prompt/history disclosure.
3. Future malicious repository text → model/tool loop → attempted permission
   expansion; exact tool scopes and explicit approvals must stop side effects.
4. Slow model endpoint → bounded provider slot and response timeout → capacity
  pressure; keep concurrency bounded and retain the known limitation that
  cancellation before the first response chunk cannot close the socket yet.
5. Future artwork change → unreviewed upstream asset → licensing conflict;
   retain the current independently drawn sprite and review new assets.
6. Plugin package → MCP stdio or remote transport → tool result/model loop;
   package validation, trust, exact permissions and resource bounds must stop
   the package from widening runtime authority.

## Review status

This is an evidence-linked engineering model, not a security certification.
File edits and manual shell commands require per-proposal human approval. Approved shell uses Bubblewrap on Linux (`shell.sandbox.bubblewrap`), Seatbelt on macOS (`shell.sandbox.seatbelt`), or a Windows AppContainer + Job Object wrap (`shell.sandbox.windows`) when the backend is available; unset/invalid defaults fail closed; only explicit auto permits unsandboxed fallback and off disables wrapping. The Windows wrap grants workspace ACL to the AppContainer SID, denies network by default (capability SIDs added on allow), and limits process-tree lifetime and job resources; it is not Codex-level WFP/LPAC, and inherited environment may still carry credentials. `VEASEL_SHELL_SANDBOX=require` fails closed when the platform backend cannot wrap. Trusted MCP stdio defaults to fail-closed OS sandboxing; explicit `VEASEL_MCP_STDIO_SANDBOX=off` runs it unsandboxed with a warning. On Linux it uses Bubblewrap by default when `bwrap` is present (capability `mcp.stdio.sandbox.bubblewrap`); on macOS it uses Seatbelt by default when `/usr/bin/sandbox-exec` is present (`mcp.stdio.sandbox.seatbelt`); on Windows it uses AppContainer + Job by default when available (`mcp.stdio.sandbox.windows`; PLUGIN_ROOT/PLUGIN_DATA ACL; network capability SIDs always on). Missing backends fail closed by default; only explicit `auto` falls back unsandboxed, while `off` disables wrapping. Autonomous shell commands are separately opt-in and require the platform OS sandbox with a filtered environment (Linux/macOS) and fail closed if setup fails. The sandbox is best-effort containment, not a VM boundary.
